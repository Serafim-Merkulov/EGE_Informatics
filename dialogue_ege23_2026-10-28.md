Если речь про привычную задачу с исполнителем, её идея такая.

Исполнитель умеет выполнять несколько команд, например:

- прибавить 1;
- умножить на 2.

Нужно узнать, **сколько последовательностей команд превращают начальное число в конечное**. Иногда нужно обязательно пройти через определённое число или избежать запрещённого.

Например, из **2 в 5** можно попасть тремя программами:

```text
2 → 3 → 4 → 5    (+1, +1, +1)
2 → 3 → 5       — нельзя: команды +2 нет
2 → 4 → 5       (+1, +1, +1 уже показана выше?)
```

Удобнее сразу различать именно команды. Правильные три программы:

```text
+1, +1, +1:  2 → 3 → 4 → 5
×2, +1:      2 → 4 → 5
```

Здесь на самом деле **две программы** — поэтому важно считать последовательности допустимых команд, а не придумывать переходы между числами.

На Python это решается короткой рекурсивной функцией:

```python
def f(x, end):
    if x == end:
        return 1
    if x > end:
        return 0

    return f(x + 1, end) + f(x * 2, end)

print(f(2, 5))  # 2
```

`f(x, end)` означает «сколько программ ведут из `x` в `end`».

- **Достигли цели → `1`**: нашли один подходящий способ закончить программу.
- **Перешли за цель → `0`**: вернуться нельзя, поскольку обе команды увеличивают число.
- **Иначе складываем** способы для двух возможных первых команд.

Если нужно **обязательно пройти через 10**, путь разбиваем на две части и перемножаем количества:

```python
print(f(2, 10) * f(10, 25))
```

Каждую программу первой части можно продолжить любой программой второй.

Если число **15 запрещено**, добавляем проверку перед проверкой достижения цели:

```python
if x == 15:
    return 0
```

Главное правило: **варианты следующей команды складываем, участки через обязательную точку перемножаем**. Такой шаблон подходит, когда команды строго увеличивают число; для уменьшающих команд условие выхода меняется.

**1. Что представляет собой задача**

Представь сеть дорог:

- **вершины** — пункты;
- **рёбра** — дороги между ними;
- **вес ребра** — длина дороги, время или стоимость;
- **ориентированный граф** — дороги со стрелками: идти можно только в указанную сторону;
- **ациклический граф** — нельзя, следуя стрелкам, вернуться в ту же вершину.

Длина пути — **сумма весов всех его рёбер**. Это не обязательно количество переходов.

Возьмём небольшой граф:

| Откуда | Куда | Вес |
|---:|---:|---:|
| 1 | 2 | 2 |
| 1 | 3 | 5 |
| 2 | 3 | 1 |
| 2 | 4 | 6 |
| 3 | 4 | 3 |

Из 1 в 4 существуют три пути:

| Путь | Длина |
|---|---:|
| 1 → 2 → 4 | 2 + 6 = **8** |
| 1 → 3 → 4 | 5 + 3 = **8** |
| 1 → 2 → 3 → 4 | 2 + 1 + 3 = **6** |

На одном примере получаются разные ответы:

- кратчайший путь — **6**;
- самый длинный — **8**;
- количество всех путей — **3**;
- количество кратчайших путей — **1**.

**Всегда начинай с вопроса: что именно нужно посчитать?**

**2. Кратчайший путь: основная идея**

Обозначим через `shortest(v)` минимальную длину пути **из вершины `v` до финиша**.

Из вершины 2 можно:

- сразу перейти в 4: стоимость `6`;
- перейти в 3, затем добраться до 4: стоимость `1 + shortest(3)`.

Поэтому:

```text
shortest(2) = min(6, 1 + shortest(3))
           = min(6, 1 + 3)
           = 4
```

А из вершины 1:

```text
shortest(1) = min(2 + shortest(2), 5 + shortest(3))
           = min(2 + 4, 5 + 3)
           = 6
```

Мы свели большую задачу к таким же задачам для соседних вершин. Это **динамическое программирование**: ответ для каждой вершины вычисляем один раз и сохраняем.

Вот полностью рабочий пример для ациклического графа:

```python
from functools import cache

# g[v] — список пар (куда ведёт ребро, его вес)
g = {
    1: [(2, 2), (3, 5)],
    2: [(3, 1), (4, 6)],
    3: [(4, 3)],
    4: []
}

finish = 4

@cache
def shortest(v):
    if v == finish:
        return 0

    return min(
        (weight + shortest(u) for u, weight in g.get(v, [])),
        default=float('inf')
    )

print(shortest(1))  # 6
```

Почему такие значения:

- на финише возвращаем **0**: оставшаяся длина равна нулю;
- из тупика возвращаем **бесконечность**: пути до финиша нет;
- `@cache` запоминает ответы, чтобы не вычислять одни и те же участки многократно.

Тупик нельзя оценивать нулём: иначе программа сочтёт его выгодным завершением пути.

**3. Количество путей: вместо минимума — сумма**

Пусть `count(v)` — количество путей из `v` до финиша.

Если из вершины можно пойти в 2 или 3, складываем:

```text
count(1) = count(2) + count(3)
```

Для нашего графа:

```text
count(4) = 1
count(3) = 1
count(2) = 1 + 1 = 2
count(1) = 2 + 1 = 3
```

Код использует тот же словарь `g`:

```python
@cache
def count(v):
    if v == finish:
        return 1

    return sum(count(u) for u, weight in g.get(v, []))

print(count(1))  # 3
```

**Почему на финише единица?** Есть один способ успешно завершить уже пришедший туда путь: больше ничего не делать.

В тупике сумма пустого набора равна нулю — ни одного подходящего пути.

Сравни две задачи:

| Что вычисляем | Ответ на финише | Ответ в тупике | Как объединяем варианты |
|---|---:|---:|---|
| Минимальную длину | 0 | `+∞` | `min(вес + ответ соседа)` |
| Максимальную длину | 0 | `−∞` | `max(вес + ответ соседа)` |
| Количество путей | 1 | 0 | `sum(ответы соседей)` |

Максимальную длину этим способом также ищут **в ациклическом графе**.

**4. Как прочитать граф из файла**

Допустим, в учебном файле каждая строка содержит:

```text
откуда куда вес
```

Тогда чтение выглядит так:

```python
g = {}

with open('23.txt') as file:
    for line in file:
        if not line.strip():
            continue

        a, b, weight = line.split()
        a = int(a)
        b = int(b)
        weight = float(weight.replace(',', '.'))

        g.setdefault(a, []).append((b, weight))
```

После чтения можно использовать функцию `shortest`.

Но **формат файла нужно сверять с условием**:

- если первая строка содержит количество вершин или рёбер, её читают отдельно;
- если весов нет, в строке будет только два числа;
- если все веса целые, удобнее использовать `int`;
- `split()` без аргументов обрабатывает и пробелы, и табуляцию.

Не добавляй обратное ребро `b → a`, если граф ориентированный.

**5. Варианты с дополнительными условиями**

Это полезные тренировочные усложнения базовых задач.

**Путь обязательно проходит через вершину `K`.**

Для количества путей в ациклическом графе:

```text
Количество(S → K → T) =
Количество(S → K) × Количество(K → T)
```

Каждую первую часть можно соединить с каждой второй.

Для минимальной длины:

```text
Минимум(S → K → T) =
Минимум(S → K) + Минимум(K → T)
```

Оба участка должны существовать.

**Путь не должен проходить через `K`.**

Добавляем проверку перед обработкой финиша:

```python
# При подсчёте путей:
if v == forbidden:
    return 0

# При поиске минимальной длины:
if v == forbidden:
    return float('inf')
```

Несколько запрещённых вершин удобно хранить в множестве:

```python
forbidden = {7, 12, 19}
```

И проверять `if v in forbidden`.

**Нужно ровно `k` переходов.**

Одной текущей вершины недостаточно. Нужно помнить ещё, сколько переходов осталось:

```python
@cache
def count_exact(v, k):
    if k == 0:
        return int(v == finish)

    return sum(
        count_exact(u, k - 1)
        for u, weight in g.get(v, [])
    )
```

Вызов `count_exact(start, 5)` считает пути ровно из пяти рёбер.

**Нужно количество именно кратчайших путей.**

Это не количество всех путей. Сначала вычисляем минимальные расстояния, затем при подсчёте оставляем только рёбра, удовлетворяющие условию:

```text
shortest(v) = weight(v, u) + shortest(u)
```

Такие рёбра позволяют продолжить путь, сохранив его минимальную длину. Сравнение дробных весов здесь требует аккуратности.

**6. Главные подводные камни**

**Номера вершин не задают порядок движения.**

Ребро `20 → 3` вполне допустимо. Поэтому из старого задания про исполнителя нельзя переносить проверку:

```python
if v > finish:
    return 0
```

Для графа она неверна.

По той же причине обработка вершин в порядке `1, 2, 3, ...` работает только при подходящей нумерации. В общем случае нужен **топологический порядок** — такой, при котором начало каждого ребра обрабатывается раньше его конца. Рекурсивные решения выше не требуют числовой упорядоченности.

**Самое дешёвое ближайшее ребро не гарантирует кратчайший путь.**

Можно сначала пройти ребро весом 1, а затем быть вынужденным пройти ребро весом 100. Другой путь с первым ребром весом 5 может оказаться короче целиком. Сравнивать нужно полные суммы.

**Рекурсия с `@cache` не защищает от циклов.**

Для цикла `1 → 2 → 1` функция снова вызовет себя до получения готового ответа. Наши шаблоны предполагают ациклический граф. Для кратчайших путей в графе с циклами алгоритм выбирают отдельно; например, при неотрицательных весах применим алгоритм Дейкстры.

**Нельзя многократно прибавлять количества путей по всем рёбрам без продуманного порядка.**

При повторном проходе уже учтённые пути будут добавляться снова. Это отличается от поиска минимума, где повторное сравнение само по себе не увеличивает ответ.

**Округление делают в конце.**

Если требуется целая часть положительной длины:

```python
print(int(answer))
```

`round(answer)` решает другую задачу. Также нельзя отбрасывать дробные части отдельных рёбер до сложения.

Для точных десятичных весов около целочисленной границы `float` может дать погрешность. Надёжные варианты — `Decimal`, созданный из текста, или перевод всех весов в целые единицы, например сотые.

**Кэш зависит от условий задачи.**

Если поменял `finish`, граф или запрещённые вершины, старые ответы в кэше остаются. Перед новым расчётом нужно очистить соответствующий кэш:

```python
shortest.cache_clear()
```

Либо передавать меняющиеся условия аргументами функции.

**7. Небольшая проверка понимания**

Для графа из начала разбора попробуй самостоятельно получить:

1. Количество путей из 1 в 4, проходящих через 2.
2. Минимальную длину пути из 1 в 4 без посещения 3.
3. Количество путей из 1 в 4 ровно из двух рёбер.
4. Количество самых длинных путей из 1 в 4.

Ответы для самопроверки: **2; 8; 2; 2**.

Первый навык, который стоит закрепить: уметь объяснить, **почему для длины на финише возвращается `0`, а для количества путей — `1`**. После этого шаблоны становятся понятными, и их гораздо легче изменять под условие.

Здесь уже есть первая ловушка: **самый дешёвый первый шаг не обязательно ведёт к самому дешёвому полному пути**. После перехода в 4 потребуется ещё добраться до 100.
